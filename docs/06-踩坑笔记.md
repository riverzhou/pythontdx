## 1. PowerShell 里 `npm` 报「running scripts is disabled」

**现象**

```
npm : File C:\Program Files\nodejs\npm.ps1 cannot be loaded because
running scripts is disabled on this system.
```

**原因**
Windows PowerShell 默认执行策略是 `Restricted`。在 PowerShell 里输入 `npm` 时，
解析到的其实是 `npm.ps1`（而不是 `npm.cmd`），于是被执行策略拦下。

**解决**

```powershell
npm.cmd install                            # 方案 A：绕过 .ps1
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned   # 方案 B：一劳永逸
```

## 2. Electron 装好了，但没有 `electron.exe`

**现象**
`npm install` 成功，但 `node_modules/electron/dist/` 不存在，运行时报
`Electron failed to install correctly`。

**原因**
**Electron 44 已经取消了 `postinstall` 脚本**，改成「第一次被 `require` 时惰性下载」。
所以 `npm install` 之后看不到二进制是正常的，它会在第一次 `npm run dev` 时才去下载。
（顺带一提：新版 npm 默认还会拦截依赖的 install scripts，esbuild 之类的包也会被拦，
但 esbuild 的平台二进制是通过 optionalDependencies 装的，通常不受影响。）

**解决**

```powershell
$env:ELECTRON_MIRROR = 'https://npmmirror.com/mirrors/electron/'
$env:ELECTRON_CUSTOM_DIR = '{{ version }}'
node node_modules/electron/install.js
```

其中国内网络下 **`ELECTRON_MIRROR` 是必须的**（GitHub Releases 基本不可达），
而 `ELECTRON_CUSTOM_DIR={{ version }}` 也是必须的——npmmirror 的目录结构是
`/44.4.3/`，不是 GitHub 的 `/v44.4.3/`。

项目已经把这两项写进 `.npmrc`，npm 会把它们注入成 `npm_config_*` 环境变量传给子进程，
所以正常 `npm install` 就能自动走镜像。

**验证镜像配置是否生效**：

```powershell
npm run env | Select-String electron
# npm_config_electron_custom_dir={{ version }}
# npm_config_electron_mirror=https://npmmirror.com/mirrors/electron/
```

## 3. 分时接口 `JSON.parse` 失败

**现象**
实时行情正常，但分时图一直报「行情接口返回了非预期的数据格式」。

**原因**
我画蛇添足地给 URL 加了个 `&_var=min_data_sh600519` 参数用来「防缓存」。
**腾讯的 JSON 接口只要看到 `_var`，就会返回 JSONP**：

```
var min_data_sh600519={"code":0,"data":{...}};
```

这已经不是合法 JSON 了。

**解决**
去掉 `_var` 参数即可。缓存交给自己的 TTL 缓存层去做，不要动上游的参数。

## 4. Solid 的 `createResource` 因为 source 身份变化而反复请求

**现象**
主进程每 3 秒推一帧行情，图表却也跟着每 3 秒重新拉一次数据。

**原因**
`createResource` 内部把 source 包成了 `createMemo(source)`（见 `solid.cjs`）。
读 `props.code` 会订阅父组件传下来的响应式 getter，
而父组件每 3 秒就会产生一个新的 quote 对象——虽然 `.code` 字符串没变，
但 source 每次返回的都是**新的对象字面量**，引用不等，于是每次都被判定为「变化了」。

**解决**
用 `createMemo` 把原始值稳定下来（memo 默认做值比较）：

```ts
const code = createMemo(() => props.code)   // 字符串没变 → 不向下游传播
// ...
createResource(() => ({ code: code(), tab: tab(), ... }), fetcher)
```

**验证方式**：在 source 里打日志，正常情况应该只有「挂载时 1 次 + 定时刷新 N 次」。
我们当时看到的是 6 次（每一次行情推送都触发），加上日志后立刻定位。

## 5. Solid 1.9 的 `createResource` 返回值变了

**现象**

```
error TS2339: Property 'refetch' does not exist on type 'Resource<ChartData>'.
```

**原因**
Solid 1.9 的类型定义是：

```ts
export type ResourceReturn<T, R> = [Resource<T>, ResourceActions<T | undefined, R>]
export type ResourceActions<T, R> = { mutate: Setter<T>; refetch: (info?: R) => ... }
```

`refetch` / `mutate` 在**元组的第二个元素**上，不在 resource 本身。

**解决**

```ts
const [data, { refetch }] = createResource(source, fetcher)
```

**附带发现**：resource 处于 `errored` 状态时，**直接调用 `data()` 会抛出异常**
（`if (err !== undefined && !pr) throw err`）。
所以读取前要先判 `data.error`，或者在 `<Show when={!data.error}>` 的 fallback 里避开读取。

## 6. Solid JSX 里的 SVG 属性必须用 kebab-case

**现象**

```
error TS2322: Property 'strokeWidth' does not exist on type 'SvgSVGAttributes<SVGSVGElement>'.
Did you mean '"stroke-width"'?
```

**原因**
React 用的是驼峰（`strokeWidth`），但 Solid 直接映射到真实 DOM/SVG 属性，用的是
kebab-case（`stroke-width`）。

**解决**
统一写 `'stroke-width'`。本项目还顺手把它收进了一个 `svgProps()` 工厂函数，
让所有图标共享同一套规格，个别图标想调细描边只需传第二个参数。

## 7. `ResizeObserver loop completed with undelivered notifications`

**现象**
控制台反复出现这条告警。

**原因**
`ResizeObserver` 的回调里写信号 → 触发重绘 → 尺寸再次变化 → 又触发回调。
虽然浏览器会自动容错（不会真的死循环），但告警很吵。

**解决**
在回调里做**值比较**，尺寸真的变了才写信号：

```ts
setSize((prev) => (prev.width === w && prev.height === h ? prev : { width: w, height: h }))
```

## 8. 港股的字段布局和 A 股完全不同

**现象**
把 A 股的解析逻辑直接套到港股上，市净率位置显示的是 `TENCENT`，涨停价位置显示的是 52 周高点。

**原因**
A 股响应有 **88** 个字段，港股只有 **78** 个，而且从下标 30 往后含义就分叉了：
港股下标 30 是 `2026/09/21 16:08:36`（带斜杠），A 股是 `20260921161437`（纯数字）；
港股 46 是英文名、48/49 是 52 周高低。

**解决**
按市场分派到两个解析函数（`buildAShareQuote` / `buildHkQuote`），
拿不到含义的字段一律置 `undefined`，界面用统一的 `—` 占位。
时间解析也要同时兼容两种格式，并统一按东八区换算成时间戳。

**额外注意**：港股成交量单位是**股**，A 股是**手**；
成交额 A 股字段 37 是**万元**，港股是**元**。

## 9. 接口失败会引发重试风暴

**现象**
分时接口报错的那次调试里，日志里短时间内出现了大量重复的 `trend:minute` 请求。

**原因**
上游失败 → 渲染层重新求值 → 再次 invoke → 主进程再打一次上游。
因为失败结果不进缓存，每一次都会真的发出网络请求。

**解决**
在缓存层做 **同 key 并发请求合并**：把在途的 Promise 也存起来，
同一时刻同一个 key 最多只有一个真实请求，无论上游并发调用多少次。
失败时**不写缓存**，但一定要清掉在途标记，否则后续请求会被永久挂住。

```ts
const inFlight = this.pending.get(key)
if (inFlight) return inFlight
```

这是本项目里「防御性设计」价值最高的一个改动。

## 10. 无边框窗口的按钮点不动

**现象**
自绘标题栏做完，窗口能拖动，但最小化/关闭按钮点不动。

**原因**
`-webkit-app-region: drag` 会把整个区域变成「窗口拖拽热区」，
Chromium 不再把鼠标事件派发给里面的元素。

**解决**
给所有交互元素显式声明：

```css
.titlebar__actions,
.win-controls,
.search-wrap {
  -webkit-app-region: no-drag;
}
```

**排查技巧**：如果某个按钮「看起来能 hover 但点击无反应」，
先怀疑它的祖先里有 `drag` 区域。

**原因**

## 13. 分时接口的 `qt` 快照嵌在 `data.<代码>` 里，不在顶层

**现象**
分时图上价格线画得出来，但浮层里 `涨跌幅` 永远显示 `—%`，`涨跌额` 显示成一个巨大的数（等于价格本身）。

**原因**
我把 `qt` 当成了响应的顶层字段：

```ts
// ❌ 错的
const snapshot = raw.qt?.[code] ?? []
```

实际结构是嵌在 `data.<代码>` 里的：

```jsonc
{ "data": { "sh600519": { "data": { ... }, "qt": { "sh600519": [...] } } } }
```

于是 `snapshot` 是空数组 → `Number(undefined) || 0` → **昨收 = 0**
→ 涨跌额 = 价格 − 0 = 价格本身，涨跌幅 = `∞` → 界面上被格式化成 `—%`。

**解决**

```ts
const body = raw.data?.[code]
const snapshot = body?.qt?.[code] ?? []
```

**这个 bug 是被截图抓出来的**，不是被类型检查抓出来的——因为 `raw.qt?.[code]`
在类型上完全合法（可选属性），只是永远取不到值。
它现在有一个专门的回归测试（当时在 `parse.test.ts`；v0.6 已随腾讯源删除，规则保留在历史记录里）。

**教训**：解析第三方报文时，`?.` 会掩盖「路径写错」这类错误。
关键字段要么用测试锁住，要么在解析函数里对异常值（这里是 0）显式兜底。

## 14. `000858`（五粮液）被判成了沪市

**现象**
单元测试报错：`expected 'SH' to be 'SZ'`。

**原因**
我原本写了一条「000 开头且不是 000001 就当沪市（上证系指数多为 000xxx）」的规则。
但 `000xxx` 绝大多数是**深市主板股票**（000001 平安银行、000002 万科A、000858 五粮液），
上证指数只占其中极少数几个。

**解决**
`000xxx` 一律按深市股票解释；要查指数必须显式带前缀（`sh000001`、`sh000300`）。

**教训**：遇到有歧义的编码规则时，选「绝大多数情况正确 + 少数情况有明确逃生通道」的方案，
而不是试图用规则把所有情况都猜对。**这条也是被测试逼出来的**。

## 15. Solid 的 `ref={变量}` 会被 ESLint 判为「变量从未被赋值」

**现象**

```
error  'inputElement' is always 'undefined' because it's never assigned  no-unassigned-vars
```

**原因**
Solid 确实支持这种写法，但它是**编译器的隐式赋值**：

```tsx
let inputElement: HTMLInputElement | undefined
;<input ref={inputElement} /> // 编译器偷偷生成赋值语句
```

静态分析工具看不到这个赋值，于是合理地认为变量永远是 `undefined`。

**解决**
改用显式回调，行为毫无歧义，可读性也更好：

```tsx
<input
  ref={(element: HTMLInputElement) => {
    inputElement = element
  }}
/>
```

## 16. 闭包捕获派生值 → 图表切换天数后横轴不更新

**现象**
ESLint 的 `solid/reactivity` 报警：

```
'totalSlots' captures the value of the reactive variable 'days' at setup,
but a returned function reads the capture later — it will never update.
```

**原因**
在 memo 里算出一个数字，再让返回出去的函数去读它：

```ts
const geometry = createMemo(() => {
  const totalSlots = days().length * DAY_SLOTS - 1
  return { x: (slot) => slot / totalSlots } // ⚠️ 读的是创建那一刻的闭包变量
})
```

在这个例子里，memo 每次重跑都会重建闭包，所以**实际上是对的**。
但这条规则抓的是同一类模式里真正出错的情形：
只要 `x` 被单独传递出去、活过了 memo 的那一轮，它就会永远停留在旧值上。

**解决**
按规则的建议，在函数内部重新读取响应式源：

```ts
x: (slot) => PAD.left + (slot / Math.max(1, days().length * DAY_SLOTS - 1)) * plotW
```

**教训**：不要在返回值里「捕获」派生值，要么传值本身，要么在函数里现读。
这个开销可以忽略，换来的是绝不会过期。

## 17. 用 `createMemo` 做副作用

**现象**

```
error  For proper analysis, a variable should be used to capture the result of this function call
```

**原因**
我为了「只在读数变化时通知外部」，写了一个裸的 `createMemo(() => { props.onHover(...) })`。
memo 的语义是「派生一个值」，拿它当副作用钩子用是坏味道，
而且因为没有接收返回值，读者也无法判断这里到底在算什么。

**解决**
用 `createEffect` + `on`，语义明确，触发时机也更准（只在依赖变化时执行）：

```ts
createEffect(
  on(hovered, (current) => {
    props.onHover?.(current ? { ... } : null)
  })
)
```

## 18. 新增一个 IPC 通道要改几个地方

**现象**
加了「五日分时」之后，渲染层调用 `api.trend.fiveDay(...)` 直接报 `undefined is not a function`。

**原因**
新增一个通道实际要同步改 **5 个地方**，漏一个就是运行时错误：

1. `src/shared/ipc.ts` —— 通道名常量 `IPC.xxx`
2. `src/shared/ipc.ts` —— `pythontdxApi` 接口里加方法签名
3. `src/preload/index.ts` —— `ipcRenderer.invoke` 的实现
4. `src/main/ipc.ts` —— `ipcMain.handle` 的注册
5. `src/main/services/**` —— 真正的业务实现

**好消息**：第 2 步是类型契约，漏了第 3 步会**编译报错**（对象缺少属性），
第 4、5 步漏了会在调用时报「No handler registered」。
也就是说，只要认真跑 `npm run typecheck`，这类问题基本不会跑到运行时。

**教训**：这就是「共享类型契约」的价值——把「字符串写错」和「漏实现」变成编译期错误。

## 19. 打包时卡在下载 NSIS 工具链

**现象**
`npm run build:win` 走到一半卡住，然后报网络错误。日志停在：

```
• building        target=portable file=release\0.3.0\...
• downloading     url=https://github.com/electron-userland/electron-builder-binaries/releases/...
```

**原因**
`npm install` 时下载 Electron 二进制走的是 `.npmrc` 里的 `electron_mirror`，
但 **electron-builder 打包时用的是另一套下载器**，它要下载 NSIS、7zip、winCodeSign
等工具链，默认仍然指向 GitHub Releases，国内网络不可达。

两件事容易混淆：

| 阶段                | 谁在下                | 环境变量                                                                |
| ------------------- | --------------------- | ----------------------------------------------------------------------- |
| `npm install`       | Electron 自己的下载器 | `ELECTRON_MIRROR` / `electron_mirror`                                   |
| `npm run build:win` | electron-builder      | `ELECTRON_BUILDER_BINARIES_MIRROR` / `electron_builder_binaries_mirror` |

**解决**
在 `.npmrc` 里再补一条：

```ini
electron_builder_binaries_mirror=https://npmmirror.com/mirrors/electron-builder-binaries/
```

npm 会把 `.npmrc` 的键注入成 `npm_config_*` 环境变量并传给子进程，
而 electron-builder 的 `getBinariesMirrorUrl()` 恰好会读
`npm_config_electron_builder_binaries_mirror`，所以配置一次就够了。

**验证是否生效**：重新打包时日志里的下载地址应该变成 `npmmirror.com`。

## 20. 便携版的 `unpackDirName` 并不会缓存解压结果

**现象**
我按官方文档的说明，给 `portable` 目标加了固定解压目录名，
并在配置注释里写下「第二次启动就能复用，冷启动快很多」。
实际测下来**完全没有加速**，热启动和冷启动耗时一模一样。

**原因**
我搞错了 `unpackDirName` 的作用。实测（electron-builder 26 / 2026-09）：

- 它**只决定解压目录的名字**（`%TEMP%\pythontdxPortable`），方便排查与手工清理；
- 应用**正常退出时会清理该目录**，所以下次启动依然要完整解压一遍；
- 只有进程被强杀（任务管理器结束任务）时才会残留。

也就是说，「单文件 exe 每次启动都要解压约 368 MB」这件事是**无法回避**的。

**实测数据**（清空 `%TEMP%` 后连续多次测量）：

| 产物                              | 从双击到界面就绪           |
| --------------------------------- | -------------------------- |
| 便携版单 exe                      | **约 2 秒**（3 次均为 2s） |
| `win-unpacked` 里的 exe（无解压） | **约 1 秒**（2 次均为 1s） |

**解决**
接受它，并把真实数字写进文档和配置注释。
结论：单文件免安装只比安装版慢约 1 秒，代价比预想的小；
想要更快就用 NSIS 安装包，想要「一个文件带走」就用便携版。

**第二次踩坑**：我第一次测量时把截图工具里「等待 N 秒再截图」的时间
算进了启动耗时，得出「便携版要 6 秒」的错误结论，并已经写进了配置注释和文档。
后来固定 `delay=0` 重测 3 次才拿到 2s 这个稳定值。
**测量脚本本身的固定开销必须排除掉**，否则量出来的不是被测对象。

**教训**：这是本项目里第二次由「我以为」引发的错误（第一次是 `qt` 的路径）。
**涉及性能或行为的断言，必须实测后再写进注释与文档**——
否则注释会变成误导下一个人的假信息。
这也正是 `PRINCIPLES.md` 里 Q3（声称完成前必须有可复现的证据）存在的原因。

## 21. `PYTHONTDX_CAPTURE_DELAY=0` 会让截图抛错、退出码为 1

**现象**
重新打包后复测便携版启动耗时，沿用了第 20 条的写法把截图延迟设为 0
（目的就是排除截图工具的等待时间）。结果进程**退出码是 1、也没有产出截图文件**。
第一反应是「这次打包是不是坏了 / 应用根本没起来」。

**原因**
退出码 1 不是崩溃。`src/main/capture.ts` 里只有截图失败那条路径会 `app.exit(1)`，
其余情况都是 `app.exit(0)`。延迟为 0 时，`capturePage()` 在
`did-finish-load` 之后**同一个 tick** 内执行，页面还没合成首帧，
Electron 抛 `UnknownVizError`。

用 `out/` 产物 + 开发用 Electron 复现（这样主进程控制台可见）：

| 延迟  | 结果                                                              |
| ----- | ----------------------------------------------------------------- |
| `0`   | `[capture] 截图失败： [Error: UnknownVizError]`，退出码 1，无文件 |
| `800` | `[capture] 截图已保存：…`，退出码 0                               |

**解决**

- 只测启动耗时时可以忽略这个退出码：进程此时已经打印过
  `[main] 配置文件：…`，说明引导流程已经跑完；
- 要拿到截图，就必须给页面留出合成时间（`npm run shot` 默认 4 秒）；
- 判断「应用有没有真的起来」**不要只看退出码**，要看有没有产出有效内容——
  本次截图 631 KB / 2558×1640 / 3201 种颜色，且红绿两种涨跌色都存在。

**教训**：退出码 1 在这套工具里是**有明确含义的**（截图失败），
并不是「任何异常都归它」。排查这类问题应该先读一遍自己写的错误分支，
而不是先怀疑打包产物。

## 22. 键盘交互没法截图验证：两个坑都是「量」出来的，不是看出来的

**现象**
给 K 线图加上「`↑` / `↓` 缩放可见根数」之后发现问题：`npm run shot` 只能拍到
**没按键的那一帧**——键盘交互拍不到。于是给截图工具加了一组开关
（点击 / 聚焦 / 注入按键 / 回读文本 / 求值只读表达式），让应用自己把界面点到位、
把键按下去、再把结果读回终端。

工具一上线，就抓到两个我自己没意识到的问题：

| 用例               | 第一次跑出来      | 应该是 | 原因                               |
| ------------------ | ----------------- | ------ | ---------------------------------- |
| `Up,Up`（按 2 下） | 120 根            | 80 根  | 切 tab 重建了 DOM，前 1 个按键被吞 |
| 最小窗口 1024×660  | 图例压到了 tab 上 | 不重叠 | 新加的档位标签把头部挤爆了         |

**原因**

- **按键被吞**：我一开始把「点击（切到日K）」和「聚焦图表」放在同一步里做完。
  但切 tab 会让 SolidJS 卸载分时图、挂载 K 线图，**被聚焦的那个 DOM 节点整个被替换掉了**，
  焦点随之回到 `body`，落在它之后的按键就没有落点。
  改成「点 tab → 等目标元素出现 → 再聚焦 → 按键」之后，按 2 下就是 2 档。
- **头部被挤爆**：`.segmented` 作为 flex 子项**默认会收缩**，头部一超宽，
  tab 自己先被压窄（240 → 201px），图例再压到 tab 上。
  这是量出来的，不是看出来的：`getBoundingClientRect()` 显示
  `seg: 255..456`、`legend: 432..593` —— 两者重叠 24px。

**解决**

- 工具里把「准备界面」和「聚焦」拆成前后两步，并且**等界面就绪之后**才聚焦；
- 档位标签从卡片头部搬到**图表自己的上边距**里（`x = padding.left, y = 12`）：
  那里是天然空白带，永远不会和 tab、图例、蜡烛、网格线抢位置，
  1024 最小窗口下也不必做任何响应式妥协。

**验证**（元素矩形 + SVG 实测，全程没有用眼睛看图）：

| 档位   | SVG 矩形数 | 蜡烛实体宽度 |
| ------ | ---------- | ------------ |
| 160 根 | 321        | 2.17px       |
| 80 根  | 161        | 4.34px       |
| 30 根  | 61         | 11.58px      |

按键序列 `↑↑↓↓` 回到 160 根、`↑` 连按 5 次停在 30 根（到顶不环绕），
都与纯函数的单元测试断言一致。

**教训**：**「看不了图」不应该成为「不验证」的借口。**
把要看的东西换算成能读的数——元素矩形、SVG 宽度、文本内容——
一样能发现真实的布局缺陷，而且比肉眼更早、更准（这条正好呼应 `PRINCIPLES.md` 的 Q3）。

## 23. 存了「窗口内的相对下标」，缩放后光标就指向了另一根 K 线

**现象**
用户实测 K 线缩放后反馈：**缩放生效了，但鼠标光标指着的那根 K 线漂移了** ——
按下 `↑` 之后十字光标还停在屏幕上差不多的位置，可它读出来的已经不是原来那一根。

**原因**
状态里存的是**窗口内的相对下标**（`hoverIndex`），窗口一变（160 → 80 根），
同一个下标就指向了另一根 K 线。这是典型的「**状态存了派生量**」：
相对下标 = 绝对下标 − 窗口起点，它应该被算出来，而不是被存起来。

**解决**

1. 光标改存**绝对下标**，窗口内的位置在使用处现算（`absolute - win.start`）；
2. 缩放改为**以光标为锚点**（`zoomWindow()`）：先算锚点在窗口里的比例，
   缩放后反推新起点，让它落在同一个比例上；
3. 光标走到窗口边缘时窗口跟着平移（`stepCursor()`），另加 `End` 一键回最新。

**一个躲不掉的取舍**
「锚点在屏幕上完全不动」与「窗口右侧不留白」互斥：光标贴着最新一根时，
要保持位置就得让窗口滚过最新一根、在右边空出一块。这里选择**贴合数据**，
代价是贴边缩放时光标在屏幕上会挪一点 —— 但它指的仍是同一根。
单测如实描述了这个取舍：中间位置断言比例不变，贴边位置只断言
「光标仍在窗口内、窗口不越界」。

**验证**（端到端实测，读的是浮层里的日期）：

| 按键                   | 档位         | 光标那一根   |
| ---------------------- | ------------ | ------------ |
| `←`                    | 近 160 根    | `2026-09-21` |
| `← ← ←`                | 近 160 根    | `2026-09-17` |
| `← ← ←` + `↑ ↑`        | **近 80 根** | `2026-09-17` |
| `↑↑` + `←` + 79 个 `←` | 近 80 根     | `2026-06-01` |
| `↑↑` + `←` + 81 个 `←` | 近 80 根     | `2026-05-28` |

第三行是关键：**档位从 160 变成 80，光标读出的日期没变**。
第四、五行则证明平移真的发生了 —— 若窗口不平移，两次会停在同一根。

**教训**：**状态里只存「不可推导的量」。** 能由别的状态算出来的值，
存它就迟早和源头不一致 —— 这里表现为「光标指着别人」。

## 24. `sendInputEvent` 的 `keyCode` 要加速器键名，写错不报错、只是没反应

**现象**
用刚做好的按键注入复测光标功能，六个用例**全部没反应**：档位一直是 160 根，
浮层也不出现。唯一生效的是 `End` —— 因为它正好两种写法同名。

**原因**
`window.webContents.sendInputEvent({ keyCode })` 收的是 **Electron 加速器键名**
（`Up` / `Left` / `Esc`），我传的是 DOM 的 `ArrowUp` / `ArrowLeft`。
连一条错误信息都没有：事件发出去了，只是没人认得，**静默失效**。
（先前验证缩放时用的恰好是 `Up,Up`，所以这个坑一直藏着没暴露。）

**解决**
工具里加一张别名表，两种写法都收：

```ts
const KEY_ALIASES = {
  ArrowUp: 'Up',
  ArrowDown: 'Down',
  ArrowLeft: 'Left',
  ArrowRight: 'Right',
  Escape: 'Esc',
  Enter: 'Return'
}
```

**顺带一个方法论**：这类会「静默失效」的工具，必须让它自己把结果**回读**出来。
如果只是「按下键、截张图」，我要么得用眼睛看图（看不了），
要么就会把「没反应」误判成「功能没做」—— 事实上我第一眼就是这么以为的。

**教训**：**外部接口的「名字」最容易静默出错。** 编译器管不到字符串参数，
所以要么把它收窄成联合类型，要么就兼容多种写法。

## 25. Electron 注入的滚轮 deltaY，和页面收到的不是同一套单位

**现象**
给 K 线加上滚轮缩放后，用截图工具注入 `deltaY: -100`，**界面一点反应都没有**：
档位不动、光标也不出现。而键盘上的同一个功能完好 —— 看起来就像「滚轮压根没接上」。

**排查**（关键是别猜，直接量）

1. 先在页面里**合成**一个 `deltaY: -100` 的 wheel 事件派发给图表元素：
   档位**立刻**从 120 变 100，浮层也出来了 —— 说明监听、累加器、锚点、渲染全是对的，
   问题只在「注入的事件」这一侧；
2. 那就把渲染层**实际收到**的 deltaY 读回来：注入前装一个记录器
   （`window.addEventListener('wheel', (e) => deltas.push(e.deltaY), { capture: true })`），
   注入后再打印。结果是 **`[50]`** —— 而我发出去的是 `-100`。

**原因**
Electron 的 `mouseWheel` 与 DOM 的 `WheelEvent` 之间隔了两层换算。
本机实测（Windows，`devicePixelRatio = 2`）：

| 注入的 deltaY | 渲染层收到 |
| ------------- | ---------- |
| `-100`        | `+50`      |

即**符号相反、数值除以 `devicePixelRatio`**：注入的算「内容滚动方向 + 设备像素」，
DOM 的算「滚轮增量 + CSS 像素」。50 连累加器的阈值（100）都不到，
于是每一次滚轮都被安静地丢掉 —— 而这个「安静」正是最难查的地方。

**解决**
工具里按实测换算 `deltaY: -deltaY * devicePixelRatio`，并且**每次注入后自检**：
把请求值与实收值一起打出来，不一致就告警。

```
[capture] 滚轮：请求 DOM deltaY = [-100, -100] → 实收 [-100,-100]
```

**教训**：**跨进程 / 跨框架的「同名参数」最危险** —— 名字一样、单位不一样，
编译器还管不到。凡是这种边界，都要先**量一次真实值**再写换算，
而且最好把「量」固化进工具里，让它以后自己告警。

## 26. 程序化 `click()` 不移动焦点 —— 于是「键盘要先点一下」这个坑复现不出来

**现象**（用户实测反馈）

> 「第一次用键盘上下键的时候，焦点会跑掉，跑到上面的日K线标签上。」

功能本身是好的：**点过图表**之后 `↑↓` 一切正常，只有第一次按的时候不对。

**先把可能性砍掉**

搜遍渲染层，只有三处键盘处理：侧栏改名框、搜索框、图表自己。
没有任何代码会把焦点挪到 tab 上 —— tab 就是三个普通 `<button>`，
既不是 radio，也没有 roving tabindex。那就只剩一个解释：
**按下的那一刻，焦点本来就在那个按钮上**。

**复现**（这里踩了工具自己的一个坑）

截图工具原来的「点击」是 `element.click()`。而**程序化点击不会移动焦点** ——
焦点是 `mousedown` 的**默认行为**，`click()` 只是派发事件，没有这一步。
于是之前每一次自动化验证里，焦点其实都停在 `body` 上，
「点完 tab 焦点留在按钮上」这个真实场景一次都没被摆出来过。

给工具补上真实指针（`mouseMove` / `mouseDown` / `mouseUp`）之后，一次就复现了：

| 用例                               | 档位       | `document.activeElement`   |
| ---------------------------------- | ---------- | -------------------------- |
| 真实点「日K」→ 鼠标移到图上 → `↑`  | 40（没变） | **`segmented__item｜日K`** |
| 显式 `.focus()` 图表 → `↑`（对照） | 40 → 35    | `chart-host`               |

**根因**

图表的键盘监听挂在**图表自己**身上，等于「必须先点它一下」；
而滚轮挂在同一个元素上、**不用点就能用**。同一张图两套规则，
用户的第一次尝试必然落进缝里：`↑` 落在 tab 按钮上，
Chrome 又因为「刚刚发生了键盘操作」把 `:focus-visible` 的焦点圈画到了那个按钮上 ——
看到的就是「焦点跑到标签上去了」。

**解决**

把键盘归属改成一条明确的规则，抽成纯函数单测（`lib/chart-keys.ts` 的 `chartOwnsKeys`）：
**指针在图上，或图有焦点** → 归这张图；事件落点在输入框里 → 一律让路
（搜索框要用 `↑↓` 选联想项）。监听改挂 `window`（否则指针在图上也没人接），
接管时顺手 `focus()` 把焦点收回图表，免得「现在是谁在响应键盘」在界面上看不出来。

**教训**：**「操作方式不一致」本身就是一个 bug，不是体验问题。**
同一个控件，鼠标能用而键盘要先点一下，用户第一次一定踩空；
而且失败现场（焦点跑到别的控件上）会把人引向完全错误的猜测方向。

另一半教训是给测试的：**测试替身的行为差异要当成风险**。
`click()` 与真实点击只差一个焦点转移，差的恰好就是这次 bug 能不能被复现出来。

## 27. 通达信握手发多了，行情全变空包

**现象**

照着 pytdx 发 `setup1 / setup2 / setup3` 三连包，握手看起来成功（每条都有 189/596 字节响应），
但紧接着的 `0x053e` 五档请求只回 4 字节：`01 05 00 00`。
换主站、换代码、单只/批量都一样；而代码数量 `0x044e`、代码表 `0x044d` 却正常。

**原因**

三连包会让服务端进入**旧版会话**。旧版会话下行情请求按旧格式解析，
返回的 4 字节是状态/数量 stub，不是真实行情。

**解决**

**只发一条 `0x000d`，data = `[0x01]`。** 不要 setup2/setup3。
改完之后五档、K 线、分时全部正常。

**教训**：开源实现（pytdx 最后更新于 2021）能连通不代表协议还对；
要拿**真实响应长度和字段**验证，而不是「没抛异常就算成功」。

## 31. Python sidecar 的 stdout 不能混日志

**现象**

应用偶发「行情桥接进程返回未知错误」，或 JSON 解析失败。

**原因**

Python 里任何 `print()` 都会写到 stdout，和 JSON Lines 抢同一根管道。

**解决**

- 业务日志一律 `print(..., file=sys.stderr)`；
- stdout 只允许 `json.dumps(response) + "\n"`；
- 主进程把 stderr 逐行加 `[tdx-bridge]` 前缀打到终端；
- Windows 下还要 `sys.stdin/stdout.reconfigure(encoding='utf-8')`，
  否则中文会按 GBK 编码，主进程按 UTF-8 解会乱码。

## 32. Git Bash 会把 `/S` 变成 `S:/`，静默安装其实弹了 GUI

**现象**

`./pythontdx-0.9.1-setup.exe /S /D=...` 退出码 0，但安装目录不对；
用户反馈「没有静默，是我手动点的」。

**原因**

MSYS2 的参数路径转换：所有以 `/` 开头、像路径的参数都会被改成 Windows 路径，
`/S` 变成 `S:/`，NSIS 收不到静默开关，于是走图形向导。`/D=` 里的反斜杠若不加引号，
还会被 bash 吃掉一层。

**解决**

```bash
MSYS2_ARG_CONV_EXCL='*' ./pythontdx-0.9.1-setup.exe /S '/D=D:\path\to\install'
```

或 PowerShell `Start-Process -ArgumentList '/S','/D=...'`。
判据不是退出码（GUI 点完也返回 0），而是「几秒内返回 + 安装目录出现」。
卸载器同理。

## 35. F10 的表格是 `│`，不是 `|`

**现象**

F10 公司资料整页都是错位的竖线和空格；财务表数字对不上列。

**原因**

`0x02d0` 返回的是固定宽度文本，表格竖线是 ULC 框线 `│`（U+2502），
旧解析正则只写了 ASCII `|` 和全角 `｜`，所以一行表格都没识别出来；
中文是双宽字符，`<pre>` 里空格对齐在比例字体下必然散架。

## 36. 单架构 Mach-O 的魔数是小端，`readUInt32BE` 读不到

**现象**

macOS 第一次打包，`before-pack` 报「macOS 包需要 Mach-O 版 sidecar，当前不是
Mach-O」，可 `file python/dist/tdx-bridge` 明明写着
`Mach-O 64-bit executable arm64`。

**原因**

thin Mach-O 的 magic 在文件里是小端存储的 `cf fa ed fe`（数值 0xfeedfacf）；
旧检查用 `readUInt32BE(0)` 去比较 `0xfeedfacf`，永远不相等——读出来是
`0xcffaedfe`。系统自带的二进制大多是 universal（`ca fe ba be`，大端），
所以这个错误一直没暴露，直到 Nuitka 产出单架构 sidecar。

**解决**

- thin 头按小端读 magic 和 cputype；universal 才按大端读 fat 表
  （64 位 fat 的表项是 32 字节，不是 20）；
- 顺带用 `context.arch` 校验架构，防止「壳和 sidecar 架构错配」的坏包；
- 测试用合成的 thin/fat 头，不依赖开发机上的系统二进制是不是 universal。

## 37. 系统代理会接管 7615，curl 却看不出来

**现象**

同一份 Python 代码，Linux/Windows 正常；macOS 上 F10 公告/估值/财务/新闻全部
12 秒超时，`audit:data` 只跑到「公告」就中断。同一个地址 `curl` 直连 0.2 秒
返回 200。

**原因**

- `python/tdx_f10.py` 用 `build_opener(ProxyHandler({}))` 统一直连；
- 回归测试起一个本地 HTTP 服务，把 `http_proxy` 指向必然拒绝的端口，
  断言请求仍然成功（走代理就会失败）；
- 排查先跑 `python3 -c "import urllib.request;print(urllib.request.getproxies())"`，
  再看 `scutil --proxy`，别一上来就怀疑通达信服务器。

## 40. 不签名下载后不是「少个提示」，是「已损坏」

**现象**

自己本机跑得好好的 dmg，传到 GitHub 或网盘后，别人下载、拖进 `/Applications`、
双击，macOS 报「已损坏，无法打开，你应该将它移到废纸篓」——没有「仍要打开」入口。
但同一台机器上直接运行本机构建的 `.app` 完全正常。

**原因**

- 浏览器/网盘下载会给文件打 `com.apple.quarantine`，本机构建没有这个标记，
  所以本地看不出问题；
- Electron 主程序里那点 `linker-signed` 的 ad-hoc 签名只覆盖可执行文件，
  整包没有 `_CodeSignature/CodeResources`，`spctl` 会报
  `code has no resources but signature indicates they must be present`；
- arm64 Mac 对签名完整性更严格，Gatekeeper 直接按「已损坏」处理，
  而不是给出可以放行的「无法验证开发者」。

**解决**

- `electron-builder.yml` 里设置 `mac.identity: '-'`（electron-builder 26 明确支持
  ad-hoc 整包签名），并设 `hardenedRuntime: false`：ad-hoc + hardened runtime
  会触发 library validation，需要额外 entitlement，而这里不需要公证；
- 签名后 `codesign --verify --deep --strict` 通过，包内含
  `_CodeSignature/CodeResources`（Sealed Resources version=2）；
  下载方看到的是「Apple 无法验证」，可以去「系统设置 → 隐私与安全性 → 仍要打开」，
  或执行 `xattr -dr com.apple.quarantine /Applications/pythontdx.app`；
- **ad-hoc 不是可信签名**：`spctl -a` 仍然拒绝，不能消除警告；
  要无警告双击安装，只能 Developer ID + 公证（付费账号）；
- 发版流程里要验证的是 `.app` 整包，不是主可执行文件：
  `codesign --verify --deep --strict` + 检查 `Sealed Resources`。

## 41. 打开软件十几秒才出分时图：涨跌家数挤在 sidecar 队列前面

**现象**

macOS 冷启动，从页面加载到 `.chart-svg` 出现 **14.97 秒**；Linux/Windows 没有

```text
9.805 -> refresh          # 首笔行情才排到
9.844 -> minute           # 分时图才排到
```

  priority，分时漏了。`minute` / `five_day` 现在都插到队首；
- 组件用 `createEffect` + `onCleanup(scheduleBreadth(...))`，状态变化自动取消；
- 新增 `breadth.test.ts`：未 live 不启动、延迟/轮询、取消。

> 独立 sidecar 方案试过后已撤回：直接测 sidecar 只有 2 秒，问题不在进程架构；
> 保持单 sidecar、与 Windows/Linux 同一套代码，只修请求顺序。

**验证**

同一台机器、同一份状态、默认分时 tab，打包版从页面加载到 `.chart-svg`：

| 版本                      |                    耗时 |
| ------------------------- | ----------------------: |
| 修复前                    |                14,971ms |
| 只修涨跌家数              | 4,200 / 4,223 / 4,317ms |
| 再加分时 priority（3 次） | 3,015 / 2,895 / 2,971ms |

- sidecar onefile 冷启动仍要 1.8~2.2 秒；磁盘/解包抖动时偶发到 8 秒；
- 首图出来后，涨跌家数仍会在后台占用 7.5 秒 sidecar 队列；要彻底消除需要

- 本轮只打 tag、不重打/不发布 dmg（等 1.0）。

## 42. 冷启动不是网络慢：Gatekeeper 首次扫描 8.5 秒 + 涨跌家数独占 5.7 秒

**现象**

0.14.3 冷启动仍然「特别久」，而且不是行情服务器慢：直接测 sidecar
`ping` 偶发 8.5 秒，之后 `minute` 只有 0.1 秒。看请求 trace：

```text
6.394 -> trades
6.453 -> market_breadth       # 整包扫描
12.115 <- market_breadth      # 独占 5.7 秒，trades/refresh/minute 全停
12.115 -> trades
```

**两个本地逻辑等待**

1. **macOS Gatekeeper 首次执行扫描**，不是解包、不是 CPU：Nuitka standalone
   目录（没有解包）首次也要 **7.75 秒**，第二次 **0.09 秒**；复制到新路径
   首次 **1.82 秒**、第二次 **0.09 秒**。`syspolicyd` 日志显示它在逐个扫描
   新 dylib 的 provenance。onefile 每次启动用新临时目录，所以每次都被当成
   新二进制扫描；固定缓存路径后只扫第一次，之后 **0.28 秒**。
2. `market_breadth` 一个命令扫 70 页，独占串行 sidecar 5.7 秒；页间没有任何机会
   让 priority 的图表请求插队。

**解决（仍是单 sidecar，没有独立进程）**

- 分时/五日 localStorage 快照：ChartPanel 先用上一帧画图（标注「离线缓存」），
  网络回来覆盖；实测首屏 **404ms**，不再等 sidecar；
- macOS `build.py` 给 onefile 指定 `{CACHE_DIR}/pythontdx/tdx-bridge/<源码指纹>`：
  固定路径复用，避免每次新路径被 Gatekeeper 重扫；源码/connect.cfg/Nuitka 版本
  变则换目录，不会用旧 sidecar；
  产物仍是**单个 `tdx-bridge` 可执行文件**（onefile），不是 standalone 目录；
  这个参数只改变解包目录，Windows/Linux 的 onefile 产物格式不变；
- `market_breadth_page`：每 8 页（640 只）发一次请求，主进程循环累加；
  页间 priority 图表请求可以插队，最多等一段 ~0.8 秒，而不是 5.7 秒；
- 新增 `trend-cache` 5 个测试、`market_breadth_page` Python 测试；
  （1.5.0 起改名为 `breadth_begin/step`，缓存与计数下沉 Python，见 `docs/23`）
- 新增 `npm run build:mac:app` / `npm run build:mac:all`，每次版本更新固定
  散装 `.app` + dmg 两件产物验证。

**验证**

- 0.14.4 打包 app，全新 userData + 清 sidecar 缓存：真首次 **10,333ms**；
  同配置第二次 **365ms**、第三/四次 **364 / 389ms**；
- 分时快照：已有快照时 **404ms** 出图（结果带「离线缓存」角标）；
- sidecar：standalone 首次 7.75s → 二次 0.09s；onefile 固定路径后 0.28~0.45s；
- `npm run check`：315 TS（32 文件）+ 164 Python（1 skipped）。

**残余**

- 首次 Gatekeeper 扫描 8.5 秒仍存在，只是被分时快照遮住；standalone 也避免不了；
  彻底消除要 Developer ID 签名 + 公证（付费）或常驻 sidecar，暂不做；
- dmg 只做本地验证，不发布 GitHub Release。

## 43. AppImage 双击没反应：不是可执行位，是 MIME 被磁盘挂载器接管

**现象**

GitHub Release 下载的 `pythontdx-1.1.0.AppImage`，终端 `./pythontdx-1.1.0.AppImage`
能启动；文件管理器双击却没有任何窗口，甚至看到镜像被挂载。

**诊断**

```bash
file --mime-type pythontdx-1.1.0.AppImage
# application/x-executable
gio info -a standard::content-type pythontdx-1.1.0.AppImage
# standard::content-type: application/vnd.appimage
gio mime application/vnd.appimage
# 默认应用程序：gnome-disk-image-mounter.desktop
```

Ubuntu/GNOME 把 `application/vnd.appimage` 默认交给 `gnome-disk-image-mounter.desktop`，
双击的语义是「挂载磁盘镜像」，不是「执行文件」。AppImage 内嵌的 `.desktop`

2. `~/.local/bin/appimage-launcher` + `appimage-launcher.desktop`：通用启动器，
   并在 `~/.config/mimeapps.list` 里把 `application/vnd.appimage` 的默认项

首次从 AppImage 启动且系统默认仍是磁盘挂载器时询问一次；拒绝后不再打扰，

## 44. `cacheOnly` 探测 miss 不应该 reject

**现象**

全新用户目录点搜索结果，控制台连续出现：

```text
Error occurred in handler for 'trend:kline': TdxError: 本地没有对应 K 线缓存
```

图最终能从网络加载，但每次点股票都刷一条异常；如果网络也失败，还可能用空图冒充缓存。

`kline(cache_only=True)` 在本地无缓存时直接 `raise TdxError`。`ipcMain.handle`

- 增加 Python 命中/未命中用例与 TS 纯函数用例。

## 45. 分时/K 线 30 秒一刷 + 九宫格只加载一次

**现象**

开盘后 1 分钟仍没有分时线；盘中分时、1 分钟 K 和九宫格像静止，切换/刷新才有变化。
集合竞价页签点数多的股票（科创板常见 150+ 点）也像价格冻结。

**根因**

- `ChartPanel` 固定 `REFRESH_MS = 30_000`；
- 主进程 `minuteCache` 10 秒、`klineCache` 60 秒，推送请求命中旧缓存；
- `MultiStockPanel` 只在打开时 `load()` 一次，没有订阅；
- 竞价列表按 09:15→09:25 顺序增长，容器不自动滚到底，最新价在视口外。

**解决**

- `lib/realtime.ts`：交易时段**所有**分时/K 线统一 1 秒；午休 30 秒、收盘 60 秒；
- 面板推送 `fresh=true` 绕过 TTL 缓存；K 线首帧全量，之后每秒只回最近 20 根，
  主进程合并进 800 根缓存，避免 9 张图每秒搬 800 根；
- 九宫格每格独立 `subscribePush`，盘中分时/K 线都是 1 秒；
- 分时第一秒：官方 09:31 之前没有点，`withOpeningBaseline` 先补 09:30 昨收基准，
  渲染层只保留当前秒一个 `liveTicks`，每秒重画最后官方点到当前价的短线；
  官方点到达后按槽位过滤，不会污染历史。K 线用 `applyLiveQuoteToKline` 补最后一根/开盘第一根；
- `QuotePoller` 下一次唤醒压在 09:15/09:30/11:30/13:00/15:00 边界上；
- 盘中价格 1 秒：`0x054c` 快照负责价格/量/额新鲜度，`0x0547` 保留五档深度；
  只靠 0x0547 时实测约 3 秒才出新价，不能宣称 1 秒；
- 竞价左侧栏兜底：没有快照/增量的代码走 `0x056a` 最后一根，
  由 `auction_quotes`（2 秒缓存）补成带 `auction=true` 的最小 Quote；
- 竞价页签顶部固定「最新」读数 + 自动跟随底部，用户上翻时暂停；
- 集合竞价阶段主行情用 `0x054c` 批量快照；快照不足时回退 `0x0547` 或 MAC。
  2026-11-03 用户反馈科创板最明显，具体主站在竞价时段的返回仍建议次日
  09:15–09:25 再抓一次报文确认。

## 46. 搜索出列表后点不中：blur 定时器与慢点击

**现象**

本地无缓存时，在主窗口搜索框输入个股，列表已经出来，点击结果却经常
「选不出来」；偶尔快点点一下又能成功。控制台没有异常。

**根因**

`SearchBox` 的输入框：

```tsx
onBlur={() => setTimeout(() => setOpen(false), 140)}
```

按下鼠标时输入框先失焦，140ms 后整个弹层被移除；如果用户按住鼠标超过
140ms 再松开，浏览器不会把 click 派发给已经移除的节点。点击越快越容易成功，
于是表现为「偶尔能选中」。

**解决**

搜索项（以及「清空」按钮）在 `mousedown` 阶段 `preventDefault()`，阻止输入框
失焦；用户松开时弹层仍然存在，`onClick` 正常执行 `commit(item)`。
弹层只会在点击外部/按 Esc/提交成功后关闭。

**验证**

- 用 CDP `Input.dispatchMouseEvent` 模拟：mousedown 后 350ms / 500ms 再 mouseup，

## 47. 周六的分时和报价属于上一交易日，不能按墙钟日期打标签

**现象**

2026-11-14 周六在 Web 端看 `sz301218`：分时图整条曲线都在 0% 以下，tooltip 的
涨跌幅也和日线对不上；日 K 还多出一根 `2026-11-14` 的空 bar（当天没有交易，
这个交易日根本不存在）。

**根因**

三处都把「墙钟日期」当成了「交易日」：

1. `0x0537` 分时响应没有日期字段，`Bridge.minute()` 用
   「日线最后一根日期 == 今天」判断分时属于哪天。周末/节假日/凌晨这个条件
   永远为假，昨收退化成 `last.close`（周五收盘 99.86），
   而正确基准是再往前一根 86.60 —— 0% 轴、涨跌幅、坐标全错；
2. `applyLiveQuoteToKline()` 只要 `last.date < label` 就补一根新 bar，
   而 `label` 来自 `quote.time`（本地接收时刻，周六），于是造出
   `2026-11-14` 这种不存在的交易日；
3. `kline_manifest` 的 `fetchedAt` 取本机时区，CI runner 是 UTC；
   `offline_sync` 又直接截前 10 位当日期，00:00–08:00 写下的缓存会被判成
   前一天，「同一天重试过就跳过」的保护因此失效或误判。

**解决**

- `Bridge.minute(code, now=None)`：按 `shanghai_clock` 的 session 判定分时
  所属交易日。交易时段（含盘前/午休）算今天；周末/节假日/凌晨取
  「日线最后一根」为交易日、昨收取再往前一根；
- `applyLiveQuoteToKline(series, quote, period, now)`：新增 `allowsNewBar()`，
  只有开盘后（含收盘后 `>=15:00`）才允许补当天 K 线；周末/节假日/凌晨
  只更新最后一根，没有历史时干脆不造；
- `fetchedAt` 统一按 `+08:00` 写；新增 `_manifest_day()`，兼容 epoch 毫秒
  与带时区 ISO，统一折算成上海日期再比较。

**验证**

- 2026-11-14（周六）06:12 真实 7709：`market_status` 返回
  `today=2026-11-14 / lastTradingDay=2026-11-13 / session=weekend`；
- `minute sz301218` 返回 `date=2026-11-13 / prevClose=86.60`，240 个点，
  末点 `15:00 = 99.86`；日线末三根 `11-11 94.97 / 11-12 86.60 / 11-13 99.86`。
  修复前同一份数据会算出 `prevClose=99.86`；
- 单测：`test_tdx.TestMinuteTradingDate` 4 例（周末 / 盘前 / 盘中 / 收盘后）、
  `test_manifest_day_normalizes_epoch_and_iso`；
  TS `realtime.test.ts` 3 例（周末不补 bar / 收盘后可补 / 开盘前不补）；
- `npm run check` 372 TS + 336 Python 全绿。
