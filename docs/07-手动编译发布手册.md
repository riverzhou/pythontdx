## 一、先建立心智模型：五个容易搞混的点

| 你以为                     | 实际                                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `npm run build` 就是在打包 | 它只生成 `out/`（JS / CSS / HTML）。**真正把 Node + Chromium 运行时和 `out/` 塞进一个 exe 的是 `electron-builder`** |
| exe 是项目的一部分         | `release/` 在 `.gitignore` 里。exe 是**发布附件**，不进版本库 —— 别人 clone 下来拿不到，必须单独给                  |
| 版本号要改好几个地方       | **只改 `package.json`**。`electron-builder.yml` 用的是 `${version}` / `${name}` 占位符，会自动跟着变                |
| 打包不需要网络             | 需要。要下载 Electron 二进制与 NSIS 工具链，而且是**两套互不相干的下载器、两个镜像键**                              |
| 编译、提交、发布是一件事   | 是三件独立的事：`build` 只在本地产出文件 → `commit` 进版本库 → `tag` / `push` 才是对外发布                          |

## 二、环境前置（出问题十有八九在这一节）

### 2.1 一律用 `npm.cmd`，不要用 `npm`

Windows PowerShell 默认禁止执行脚本，而 `npm` 在 PowerShell 里走的是 `npm.ps1`，
会直接报 `npm.ps1 cannot be loaded because running scripts is disabled`。

```powershell
npm.cmd -v          # 能打印版本号就对了
```

本文所有命令都写成 `npm.cmd`。想一劳永逸也可以放开执行策略
（`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`），见 `docs/01`。

### 2.2 先修 PATH，并清掉 `ELECTRON_RUN_AS_NODE`

若 `node -v` 报的版本不对、或应用窗口**根本不出现**，在同一个终端里先执行：

```powershell
$env:Path = 'C:\Program Files\nodejs;' + $env:Path
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
```

- 前半句：某些终端环境里 PATH 被别的 `node` 垫片挡住，必须把真 Node 排到最前；
- 后半句：`ELECTRON_RUN_AS_NODE=1` 会让 Electron **退化成纯 Node 进程**——
  不报错、不崩溃，只是**永远不出窗口**，截图工具会一直等到超时。
  这是排查「界面打不开」时最容易忽略的一条。

### 2.3 确认镜像「两件套」都在

打包要下载两类东西，由 `.npmrc` 里两个**不同的键**控制，缺一不可：

```powershell
Get-Content .npmrc
```

| 键                                 | 管什么                             |
| ---------------------------------- | ---------------------------------- |
| `electron_mirror`                  | Electron 运行时二进制（约 235 MB） |
| `electron_builder_binaries_mirror` | NSIS / winCodeSign 等打包工具链    |

> 注意：`electron_custom_dir={{ version }}` 也是必须的 ——
> npmmirror 的目录结构是 `/44.4.3/`，而 GitHub 是 `/v44.4.3/`，
> 少了这一行会 404。

### 2.4 不要用管道判断成败

```powershell
npm.cmd run check | Select-Object -Last 5   # ← 这样读 $LASTEXITCODE 不可靠
```

管道会掩盖真实退出码。要判断成败就重定向到文件：

```powershell
npm.cmd run check *> $env:TEMP\check.log
Write-Host "exit=$LASTEXITCODE"             # 这才是真的
Get-Content $env:TEMP\check.log -Tail 20
```

### 2.5 本机实测基线（对照用）

| 项目             | 本机实测值                   |
| ---------------- | ---------------------------- |
| Node.js          | `v24.21.0`（要求 ≥ 20.19）   |
| npm              | `11.19.0`                    |
| git              | `2.49.0.windows.1`           |
| Electron         | `44.4.3`                     |
| `build:win` 耗时 | **约 22 秒**（工具链已缓存） |

> 首次打包要下载工具链，时间取决于网络，可能到 1~2 分钟。
> 之后走缓存，稳定在 20 秒出头。

## 三、发布流程（九步）

### ① 决定版本号

遵循语义化版本：加功能 +1 minor，只修 bug +1 patch。

> **本项目额外约定**：只改文档 / 工程配置时**不单独发版**。
> 因为源码没变，发出来的 exe 与上一版**内容完全相同**——
> 让人重新下载一个一模一样的文件是种欺骗。

### ② 改 `package.json` 的 `version`

一处生效，产物文件名与 `release/<版本号>/` 目录都会跟着变。
改完顺手确认 `electron-builder.yml` 里没有写死的版本号（本项目用的是占位符）。

### ③ 更新 `CHANGELOG.md`

把「未发布」小节里的内容归到新版本号下，写清日期与主题
（格式参考文件顶部的说明）。**实测数据要放进来**，第九节（本次发布）与第八节（上一版）都是范例。

### ④ 健康检查

```powershell
npm.cmd run check
```

必须 **exit 0**。它依次跑类型检查、ESLint、TS 单元测试（当前 366 个）、
Python 协议测试（324 个）。**开发机必须能跑 `python3`（或 `python`）**，
否则 `test:python` 会失败。

**顺带核对一件事**：测试数量与文档里写的是否一致。
本项目真的踩过这个坑 —— 文档写着 139，实际已经是 147（后来又涨到 163、179、192、196；
v0.6 删掉腾讯解析后是 157 + 17 Python），
因为文档是照批次中间状态的数字写的。

### ⑤ 打包

**先确认 Nuitka 可用**（只需一次；Linux 还需 patchelf）：

```bash
python3 -m pip install -r requirements.txt
python3 -m nuitka --version
patchelf --version
```

**不要从 Linux 交叉打 Windows 包**：`electron-builder --win dir` 会把当前平台的
`python/dist/tdx-bridge`（ELF）原样塞进 Windows 包，启动必失败。现在
`scripts/build/before-pack.cjs` 会在打包前校验 sidecar 魔数并直接报错；Windows
包必须在 Windows 上运行 `npm.cmd run build:win`。

`build:win` 会自动先跑 `npm run build:python`，把 `python/tdx_server.py`
（内含 Bridge 与 HTTP/WS 服务）打成 `python/dist/tdx-bridge.exe`，再交给
electron-builder 放进 `resources/tdx-bridge/`；`out/web` 同时复制到
`resources/web/` 作为桌面页面。

```powershell
npm.cmd run build:win            # 安装包 + 便携版，一次出两个
npm.cmd run build:win:portable   # 只要单文件便携版
npm.cmd run build:win:setup      # 只要 NSIS 安装包
```

如果只想先验证桥接程序，可以单独跑：

```powershell
npm.cmd run build:python
python\dist\tdx-bridge.exe       # 应该等到一行 JSON 输入；Ctrl+C 退出
```

产物落在 `release/<版本号>/`：

```
release/0.9.0/
├── pythontdx-0.9.0-portable.exe      ← 单文件便携版（交付物）
├── pythontdx-0.9.0-setup.exe         ← NSIS 安装包（交付物）
├── pythontdx-0.9.0-setup.exe.blockmap
├── builder-debug.yml                 ← 打包参数快照，排查用
├── win-unpacked/                     ← 未压缩目录，调试用
└── pythontdx-data/                   ← 跑过便携版后，它的数据存这儿
```

### ⑥ 实测产物（**这一步绝对不能省**）

打包命令返回 0 **不等于**产物能用。分三小步。

**(a) 让便携版自己截图**

应用内置了截图开关（`src/main/services/capture.ts`），设了环境变量才生效：

```powershell
$exe = 'release\0.9.0\pythontdx-0.9.0-portable.exe'
$env:PYTHONTDX_CAPTURE       = "$PWD\screenshots\portable.png"
$env:PYTHONTDX_CAPTURE_DELAY = '5000'      # 给行情请求留 5 秒
$p = Start-Process $exe -PassThru
$p.WaitForExit(120000) | Out-Null
Write-Host "exit=$($p.ExitCode)"
```

**(b) 测启动耗时（方法要正确）**

```powershell
$env:PYTHONTDX_CAPTURE_DELAY = '0'
$sw = [Diagnostics.Stopwatch]::StartNew()
$p  = Start-Process $exe -PassThru
$p.WaitForExit(120000) | Out-Null
$sw.Stop()
Write-Host ("{0:N2} 秒" -f $sw.Elapsed.TotalSeconds)
```

两条必须知道的规矩：

- **`delay=0` 时退出码是 1、也不会产出截图** —— 这是预期行为，不是崩溃。
  延迟为 0 时 `capturePage()` 在页面合成首帧前执行，会抛 `UnknownVizError`
  （`docs/06` 第 21 条）。此时进程早已打印过 `[main] 配置文件：…`，说明启动正常。
  这样测到的是「双击 → 页面加载完成」。
- **绝不要把 `delay=5000` 的墙钟时间当启动耗时** —— 那等于把 5 秒等待算进去了。
  本项目第一次就是这么量出「便携版要 6 秒」的错误结论并写进文档的（`docs/06` 第 20 条）。

**(c) 确认没有留下垃圾**

```powershell
Test-Path "$env:TEMP\pythontdxPortable"    # 正常退出应为 False
```

便携版每次启动都会把约 368 MB 解压到这个目录，正常退出时清理，
**被强杀（任务管理器结束进程）时会残留**，手动删掉即可。

**(d) 肉眼验收截图**

打开 `screenshots/portable.png`，重点看：

- 不是白屏、深色底纹正常；
- 涨跌颜色符合 A 股语义（**涨红跌绿**）；
- 自选股名字没有多余空格（通达信也会拿空格做对齐填充，如 `五 粮 液`，Python 侧已归一化）；
- 图表区有内容、没有画歪或溢出。

> 类型检查与单元测试永远抓不到「布局错位、颜色不可读」，
> 只有这一步能。这是 `PRINCIPLES.md` 里 U5 存在的理由。

### ⑦ 记录实测数据并提交

把产物大小、启动耗时、临时目录行为写进 `CHANGELOG.md` 的「已验证」小节。
**数字必须实测后填**，不要估算 —— 第八节的表格就是范例。

提交前先看一眼改了什么：

```powershell
git status --short
git add -u                                   # -u 只提交已跟踪文件的修改
```

中文提交信息**建议走文件**，别直接写在 `-m` 后面：

```powershell
# 用编辑器把提交信息写进 .commit-msg.tmp（UTF-8），然后：
git commit -F .commit-msg.tmp
Remove-Item .commit-msg.tmp
```

原因：本机终端环境的默认编码不是 UTF-8（`Get-Content` 会把 UTF-8 文件读成乱码），
中文直接当参数传给 git 有被写坏的风险。写成文件可控得多。

### ⑧ 打标签与推送（**对外动作，先确认再做**）

```powershell
git tag v0.9.1                    # 打标签（本地）
git ls-remote --tags origin       # 先看远端到底有没有标签
git push origin master            # 推分支
git push --tags                   # 推标签
```

- 这一步之后东西就对外可见了，**做之前先问过负责人**；
- `git push` 与 `git push --tags` 是两条独立命令，**只推分支不会带上标签**；
- 远端没有任何标签时，GitLab 上就没有可下载的 Release 页面 ——
  想让别人直接下 exe，需要建 Release 并**手动上传产物文件**
  （`release/` 不进版本库，推送不会带上去）。

> **重发同一个版本时会遇到**：`git tag v0.9.1` 报 `already exists`。
> 想让它指向新提交，得先 `git tag -d v0.9.1` 再重打。
> **只有确认远端还没有这个标签时才是安全的**（远端有的话就是改写历史，会影响别人）。

### ⑨ 社交预览图与仓库门面（手动，GitHub 没有 API）

分享到 X / 微信 / Slack / 搜索引擎卡片时，用的是 GitHub 的社交预览图；
默认卡片只是灰底仓库名，点击率很低。

- **生成**：`npm run social` → `docs/assets/pythontdx-social-preview.png`（1280×640）；
  脚本在 `scripts/dev/social-preview.py`，左侧标题/能力标签/数据规模，右侧嵌真实截图。
  换版本时改脚本里的 `VERSION` 再跑。需要 Pillow
  （`python -m pip install pillow`，只是素材工具，不属于运行时依赖）；

## 七、macOS / Linux

三平台都用 Nuitka 单文件 sidecar + electron-builder；**每个平台必须在自己的机器上构建**：

```bash
npm run build:mac        # macOS dmg（仅 Apple Silicon / arm64）
npm run build:linux      # AppImage + deb
```

macOS 打包要点（2026-11-02 实机）：

- **只交付 arm64**：2026-11-02 用户明确不需要支持 Intel，`electron-builder.yml`
  已把 macOS 目标固定为 `arch: [arm64]`。`before-pack.cjs` 会拒绝 x64 / universal
  目标，并校验 sidecar 的 Mach-O 架构；在 Intel 机器上构建会得到「arm64 外壳 +
  x64 sidecar」，同样被拦下，不会产出坏包；
- **ad-hoc 签名 / 未公证**：没有 Developer ID，`mac.identity: '-'` 做整包 ad-hoc
  签名（`hardenedRuntime: false`）。`codesign --verify --deep --strict` 通过、包内
  含 `_CodeSignature/CodeResources`；它把下载后的「已损坏」变成可放行的
  「无法验证开发者」：系统设置 → 隐私与安全性 → 仍要打开，或
  `xattr -dr com.apple.quarantine`。**ad-hoc 不能消除警告**，彻底消除需要
  Developer ID + 公证（付费账号），详见第三十五节；
- dmg 需要 `.icns`；没有时 electron-builder 会把 `build/icon.png`（512×512）转成
  `icon.icns`，本次转换成功；
- 启动时可能打印
  `sandbox_extension_issue_file failed for .../pythontdx Helper.app/...: Operation not permitted`，
  这是 ad-hoc / 未公证包的常见日志，本次实测不影响窗口、行情、图表与 F10；
- `ELECTRON_RUN_AS_NODE=1` 时 packaged 可执行文件会按 Node 启动并静默退出，
  必须 `env -u ELECTRON_RUN_AS_NODE` 再启动（Linux/macOS 都有这个问题）；
- **不想走 dmg/安装也能验证打包结果**：`open release/0.14.2/mac-arm64/pythontdx.app`
  直接运行 electron-builder 产出的 `.app`，sidecar 已内置；它和
  `npm run dev` / `npm run preview` 的区别是 `app.isPackaged=true`，会走
  `resources/tdx-bridge`。日常调试用 `npm run dev`，验证打包用这个 `.app` 或 dmg。

Linux 已用 **linux-unpacked + AppImage + deb** 验证 Nuitka + electron-builder：

- deb 已构建并解包启动验证（123 MB）；`homepage` 已补为仓库地址；
- Linux 的 **AppImage（147 MB）与 deb（123 MB）均已构建并启动验证**（2026-10-31 18:04 Parquet/DuckDB 重打包）；
- `linux-unpacked`（295 MB、sidecar 11 MB）已构建，sidecar `ping` 返回 `pong`；
  GUI 截图 `screenshots/packaged-linux.png`，行情/图表正常；
- AppImage / deb 启动均需 `env -u ELECTRON_RUN_AS_NODE`；无 FUSE 用 `--appimage-extract-and-run`。

验证命令（Linux，2026-10-30）：

```bash
PYTHONPATH=/tmp/pyi-target python3 python/build.py
npx electron-builder --linux --dir
printf '{"id":1,"cmd":"ping"}\n' | release/0.9.0/linux-unpacked/resources/tdx-bridge/tdx-bridge
env -u ELECTRON_RUN_AS_NODE PYTHONTDX_CAPTURE=/tmp/packaged.png \
  release/0.9.0/linux-unpacked/pythontdx
env -u ELECTRON_RUN_AS_NODE PYTHONTDX_CAPTURE=/tmp/appimage.png \
  release/0.9.0/pythontdx-0.9.0.AppImage --appimage-extract-and-run
dpkg-deb -x release/0.9.0/pythontdx_0.9.0_amd64.deb /tmp/deb-root
env -u ELECTRON_RUN_AS_NODE PYTHONTDX_CAPTURE=/tmp/deb.png \
  /tmp/deb-root/opt/pythontdx/pythontdx
```

**Linux / Windows x64 / macOS arm64 均已实机验收；三平台各自构建，不交叉编译。**
